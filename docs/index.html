Text-to-SQL agent: how it works, and how it got to 10/10

An interactive CLI that turns plain-English questions into executed SQL on the Chinook sample database, on any OpenAI-compatible LLM. One design idea drives everything: the LLM does the reasoning, deterministic code does the safety and control.

1How a question becomes an answer

Blue boxes are the LLM (reasoning). Gray boxes are plain Python (guaranteed behavior). Hover any box for what it does.

The LLM decidesPlain code guarantees
What the question meansOnly SELECT/WITH ever runs (whitelist + read-only connection)
Which tables and joins to useExactly one statement, comments stripped
The SQL itselfRetry limit (2), request timeout (25s), token cap (600)
How to fix SQL given the real errorExecution, timing, history size, rendering

Why not a tool-calling agent? Same observe-and-repair behavior, but every question would cost 2–3 model round-trips (~3–5s) instead of one (~1s) — and an interactive CLI needs answers in under ~3s. The four stages above are the tool boundaries: flipping stage 4 into a model-invoked tool for large schemas is a ~20-line change.

# src/agent.py — ask(), simplified
messages = [system_prompt] + history + [question]
for attempt in range(1 + max_repairs):          # 1 try + 2 repairs
    sql   = extract_sql(llm(messages))          # ```sql fence -> string
    error = guard(sql)                          # None if SELECT/WITH, single stmt
    if error is None:
        try:
            return execute(sql)                 # read-only connection
        except sqlite3.Error as e:
            error = str(e)                      # the model gets the real error
    messages += [assistant(sql),
                 user(f"That query failed: {error}. Return a corrected query.")]
return failure(error)                           # never pretend it worked

3How results are graded — and why the grader is trusted

  • Execute, then compare results — never compare SQL text. Different valid queries can produce the same correct answer.
  • Rows are compared as an unordered multiset, ignoring column names, floats rounded to 2dp. Reason: the gold answers contain rank ties (q_008, q_009) and two different playlists both named "Music" (q_006) — ordered or name-strict comparison would fail correct answers.
  • The grader graded itself first: --self-test runs the gold SQL through the same pipeline — 10/10, so harness bugs can't masquerade as model quality.
  • The baseline ran through the same harness: a naive one-line prompt (“Convert this question to SQL”) scores 2/10 — it invents tables (orders, transactions, albums) that don't exist.

Reading the pattern: the repair loop catches SQL mistakes (2 saves in run 1); it cannot catch presentation mismatches (query runs fine, columns shaped differently than expected) — those needed prompt rules — nor infrastructure spikes, which needed timeout policy. Three failure classes, three different tools.

baseline prompt's failures agent-side failures during development

Wrong-but-executing SQL — the scariest class for a tool people trust with their data — appeared zero times in agent runs: every agent failure was either visible (timeout, empty) or a column-shape mismatch with correct data.

The honest read: warm-path latency beats the 3s target by 2–10×, but roughly one request per run hits a serverless cold-replica spike. Production mitigations, in order: streaming (perceived latency), a dedicated deployment (no cold replicas), and a latency-budget retry policy.

7Cost: what one question consumes

Measured usage per question in the final runs: one call, and almost all of it is prompt.

Two levers follow directly. The system prompt (rules, schema, sample rows) is identical on every request and is nearly all of the input, so providers with prompt caching discount most of it. And since a small open model (Nemotron Lightning 30B) also scored 10/10 here at P50 0.31s, routing small-by-default and large-for-complex-schemas is a real lever, not a hope.
